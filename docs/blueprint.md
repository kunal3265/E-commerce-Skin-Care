# Clay & Kin — Storefront Design Blueprint

**Scope:** design system, page architecture, interaction rules and compliance evidence for a
single-brand skincare storefront (8 SKUs, ₹349–₹1,299, India shipping, GST at checkout).
**Status:** implemented as a working static site, not a slide deck. Every rule below is either
enforced in code or measured by a script in `scripts/`.
**Verification:** `npm run verify` (contrast + build + static audit) and
`PORT=4180 node scripts/tasks.mjs verify-browser` (axe-core, screenshots, first-viewport geometry).

| Companion file | What it contains |
| --- | --- |
| `docs/contrast-matrix.md` | 17 colour pairs with computed ratios, generated from tokens |
| `docs/palette-share.md` | measured 60-30-10 surface split per template and viewport |
| `docs/a11y-report.md` | axe-core results for 9 routes × 2 viewports |
| `docs/build-report.md` | per-route HTML weight and audit checks |
| `screenshots/` | 14 rendered captures at 1440×900 and 390×844 |

## 1. Operating objectives

The storefront has three jobs, in order of business value:

1. **Convert a first-time visitor on a phone** into a paid order without contacting support.
2. **Remove the reasons to abandon** before they are felt: unknown total cost, unknown fit,
   unknown return terms, forced account creation.
3. **Convert the first order into the second** without a support ticket: tracking, reorder,
   self-service return.

Success is measured on four numbers, not on taste:

| KPI | Definition | Instrumentation |
| --- | --- | --- |
| PDP → add-to-cart | `add_to_cart` / `view_item` | event schema §14 |
| ATC → paid order | `purchase` / `add_to_cart` | checkout steps §8 |
| Checkout completion | `purchase` / `begin_checkout` | step funnel §8 |
| 60-day repeat rate | orders 2+ / customers with 1 order | account + order data §12 |

**Non-negotiables and where they are enforced**

| Rule | Enforcement | Evidence |
| --- | --- | --- |
| 60-30-10 palette | CSS tokens only; no raw hex in components | `docs/palette-share.md` |
| 4.5:1 text contrast | Token pairs computed at build time | `npm run contrast` |
| 48×48 px targets (9 mm) | `--target-min` used by every control | tap-target probe §10.6 |
| Above-the-fold buy path | Layout budgets + sticky mobile bar | geometry table §4.3 |
| Guest checkout | No account gate in any step | static audit |
| ≤ 2 typefaces | System serif + system sans, 0 webfonts | `npm run audit` |
| ≤ 160-word descriptions | Copy budget check | `npm run audit` |
| Machine-readable offers | JSON-LD with price parity assertion | `npm run audit` |
| WCAG 2.2 AA | axe-core + manual keyboard pass | `docs/a11y-report.md` |

## 2. Colour: deploying 60-30-10

### 2.1 Role assignment

| Swatch | Hex | Budget | Applied to | Never applied to |
| --- | --- | --- | --- | --- |
| Cosmic Latte | `#FFF8E7` | 60% | page canvas, content bands, card image mats, reading surfaces | large interactive fills |
| Mocha Cream | `#E4D1B4` | 30% | header band, product cards, summary panels, sidebars, utility blocks, footer, table rules | body copy (fails contrast) |
| Deep Burgundy | `#6B1F2B` | 10% | primary CTA fill, active nav underline, selected state, progress fill, critical notice edge | secondary buttons, body text, decorative blocks |
| Mocha Ink | `#6B5340` | — | body copy on all three surfaces | — |
| Ink | `#241C15` | — | headings, prices, high-emphasis copy | — |
| Field border | `#8A6E52` | — | input and control boundaries | — |

The palette is exactly three named swatches. Everything else is a functional tone derived from
them (rules, field borders, success/warning/danger). No fourth brand colour is introduced.

### 2.2 The Mocha Cream text problem, solved without breaking the palette

Mocha Cream as type on Cosmic Latte measures **1.41:1**. It cannot carry a single word of copy,
so the brief's "body text in Mocha Cream" is satisfied by a darker tone **inside the same hue**:
Mocha Ink `#6B5340` at **6.75:1** on Latte and **4.79:1** on Mocha Cream. Mocha Cream still owns
the 30% surface budget; the words on it are legible. This is the only permitted deviation from a
literal reading of the palette, and it is the difference between a colour scheme and an
accessible one.

Full matrix: `docs/contrast-matrix.md`. Lowest text pair 4.79:1, lowest non-text pair 3.18:1,
highest 15.84:1.

### 2.3 Measured surface share (first viewport, imagery masked)

Generated by `scripts/tasks.mjs palette` from rendered pixels, not from intent.

| Template | Viewport | Latte | Mocha | Burgundy | Text/neutral |
| --- | --- | --- | --- | --- | --- |
| Home | 1440×900 | 83.6% | 12.0% | 1.4% | 2.2% |
| Shop | 1440×900 | 80.3% | 17.7% | 0.2% | 1.4% |
| PDP | 1440×900 | 79.1% | 15.2% | 3.9% | 1.5% |
| Checkout | 1440×900 | 68.2% | 28.9% | 1.2% | 1.1% |
| Home | 390×844 | 63.3% | 22.1% | 8.3% | 3.9% |
| Shop | 390×844 | 74.4% | 20.8% | 0.4% | 2.8% |
| PDP | 390×844 | 60.0% | 25.6% | 11.2% | 2.3% |
| Checkout | 390×844 | 74.1% | 16.2% | 6.3% | 2.0% |

**How to read this.** The 60-30-10 rule is a hierarchy budget, not a pixel quota that every
viewport can hit: an editorial page with one hero image and no panels has almost no secondary
surface to colour. The build lands at **60–84% Latte, 12–29% Mocha, 0.2–11% Burgundy** across
templates, with checkout closest to the literal 60/30/10 split and the home page the furthest
from it.

Two deviations are declared rather than hidden:

- **Home desktop is 84% Latte.** The first viewport is a headline, a paragraph and one image.
  Reaching 30% Mocha there would require panelling the hero copy, which trades reading comfort
  for colour accounting. Accepted. If strict parity is mandatory, the cheapest lever is a
  Mocha Cream guarantee band directly under the hero proof strip (adds ≈8 points).
- **PDP mobile is 11.2% Burgundy.** The sticky buy bar plus the selected size chip push the
  accent a point over the 10% ceiling. That bar is the single most valuable accent on the page;
  the alternative is a lower-contrast CTA in the thumb zone. Accepted, capped at 12%.

Nobody should tune these percentages by eye. Re-run the script after any surface change; the
acceptance bands are Latte 60–85, Mocha 12–30, Burgundy ≤ 12.

### 2.4 Accent inventory

Burgundy is a **transaction signal**, so its uses are enumerated:

1. Primary add-to-cart / checkout / pay buttons.
2. Active navigation underline and current-step marker.
3. Selected variant (size) border and tint.
4. Shipping-progress fill.
5. Bestseller badge fill.
6. Critical notice left edge (stock, policy change).
7. Inline link hover state.
8. Focus ring (`#551721` for 9.2:1 on Mocha).

Forbidden: body copy, headings, icon fills at rest, secondary buttons, decorative rules, section
backgrounds, more than one primary button per viewport.

### 2.5 Functional colour beyond the palette

Success `#3E7A5A` (4.79:1), warning `#7A4A12` (7.04:1), error `#8A1F2B` (8.93:1). These are
status colours, never brand accents, and every status is also labelled in text or with an icon —
colour is never the only channel.

### 2.6 Implementation rules

- Components consume tokens (`var(--surface-page)`, `var(--mocha-200)`); no hex literals outside
  `:root`.
- `--rule` (Mocha Cream) is a hairline on Latte; `--mocha-300` is the hairline on Mocha surfaces;
  `--border-field` is the control boundary at 4.47:1.
- Contrast is checked by script before deploy. Editing a token without running
  `npm run contrast` is a release blocker.

## 3. Typography and copy

### 3.1 Two families, no downloads

| Role | Stack | Why |
| --- | --- | --- |
| Display | Iowan Old Style → Palatino → Georgia (serif) | Editorial authority without a webfont request |
| Text | system-ui → Segoe UI → Roboto → Arial | Native rendering, zero layout shift, no FOIT |

Zero `@font-face` rules, zero font bytes. The trade-off is cross-platform variation in the
serif; accepted for a 0 kB font budget. If brand requires an identical serif everywhere, self-host
one variable font subset (≤ 40 kB WOFF2) and re-check CLS.

### 3.2 Scale and measure

| Token | Size | Use |
| --- | --- | --- |
| `--text-2xs` | 11 px | uppercase labels, badges (letterspaced, never body) |
| `--text-xs` | 13 px | meta, captions, stock lines |
| `--text-sm` | 15 px | secondary copy, table cells |
| `--text-base` | 17 px | body copy (minimum for long text) |
| `--text-lg` | 19 px | lead paragraphs, prices |
| `--text-xl`–`4xl` | 22–52 px, fluid | card titles, section heads, H1 |

Body line-height 1.6, headings 1.12–1.3, measure capped at **68ch** (44ch for tight columns).
Prices and quantities use tabular numerals so totals do not jitter as they update.

### 3.3 Copy contract

- Product descriptions: **76–88 words** in this build; hard budget 160, enforced by
  `scripts/tasks.mjs` (audit task).
- Structure: symptom in the customer's words → what the formula does → the proof (concentration,
  test size) → who it is not for.
- Benefit first, ingredient second, certification third. No "luxury", "clean", "clinical-grade"
  without a definition or a number behind it.
- Claims must be checkable: an ingredient concentration, "62 mm × 48 mm jar", "30-day
  returns, opened or not". A claim without a source is removed in review.

Example of the rewrite pattern actually used:

> Before: "A luxurious, deeply nourishing balm that transforms your skin."
> After: "Stings after washing? This 5% squalane balm sits on top of the barrier instead of
> soaking in, so the tightness fades before you leave the bathroom. 62 mm jar, 50 ml."

## 4. Layout and scanning

### 4.1 Grid

- 12-column shell, max content 1280 px, 16 px gutters on phones, 24–40 px on desktop.
- Breakpoints: 640, 960, 1100, 1280. Mobile-first CSS; every rule above 640 px is an enhancement.
- Reflow verified at 320 px and 400% zoom: no horizontal scroll, no clipped controls.

### 4.2 Header (F-pattern anchor)

| Zone | Content | Rule |
| --- | --- | --- |
| Top-left | Logo (48 px target) | Always returns to `/`; never a dropdown |
| Centre | Search field, 48 px tall | Placeholder shows a symptom example, not "Search..." |
| Top-right | Account, Cart with count | Count is text + `aria-live`, not colour alone |
| Second row | 6 top-level items + shipping threshold | No seventh item; overflow goes to mega-menu |

Header height 126 px desktop / 129 px mobile including the nav row. It is sticky, so the buy path
and search stay available at any scroll depth. The header sits on Mocha Cream: it is the one
structural band every template shares, which is what keeps the secondary colour present on
editorial pages.

### 4.3 Above-the-fold budgets (measured)

| Template | Viewport | H1 top | Price top | Primary CTA | Fold |
| --- | --- | --- | --- | --- | --- |
| Home | 1440×900 | 236 px | — | 544 px (Shop the set) | 900 px |
| PDP | 1440×900 | 280 px | 457 px | 728 px | 900 px |
| Home | 390×844 | 493 px | — | 769 px | 844 px |
| PDP | 390×844 | 544 px | 644 px | **775 px (sticky bar)** | 844 px |

PDP mobile sequence is deliberately reordered: gallery → title → pack facts → price → size →
sticky buy bar. The inline form button sits at 868 px, below the fold by design; the sticky bar
(69 px tall, price + Add to cart, 52 px button) covers the thumb zone from first paint. On
desktop the inline button is the primary control at 728 px, with trust marks below it at 792 px.

Home mobile spends its first 260 px on the hero image, then headline, then CTA — image first is
the correct order for a product category where the object is the argument.

### 4.4 Thumb zone and target sizes

- Primary mobile actions live in the bottom 25% of the viewport: sticky buy bar on PDP and
  full-width primary buttons in normal flow. The desktop cart summary is sticky; on mobile it
  becomes static so the checkout button follows the line items.
- Every standalone control ≥ 48×48 px. Measured: **0 non-inline controls under 48 px** across
  9 routes × 2 viewports.
- Checkbox glyphs render at 22 px, but the wrapping 48 px label is the hit area; radio options
  are full 48 px rows. The input is never the only clickable region.
- Inline links inside sentences (return policy, breadcrumbs, order item names) use the WCAG 2.5.8
  inline exception; order-item links were raised to 48 px because they are list actions, not prose.
- 8 px minimum gap between adjacent targets; 12 px between destructive and primary actions.

### 4.5 Gallery contract

Each PDP ships three images: front (packshot), texture at 3× magnification, and an in-scale
reference showing the product in a hand with a millimetre rule. The scale image is generated from
the product's quoted dimensions (6 px per mm), so the proportion is exact rather than eyeballed.
The caption states the measurement in text as well: "62 mm wide × 48 mm tall; 50 ml jar".

Minimum bar for real photography: one lifestyle image with a hand or model, one texture
close-up, consistent lighting, 4:5 crop, ≤ 60 kB at 480w and ≤ 140 kB at 960w.

### 4.6 Motion system

Motion is used to confirm interaction and to introduce below-fold content, never to delay
reading or to decorate an idle page. Every effect is `transform`/`opacity` only, so nothing
reflows and CLS stays at zero.

| Surface | Effect | Timing |
| --- | --- | --- |
| Sticky header | shadow appears after 8 px of scroll | 200 ms |
| Product card | 4 px lift, warm mocha shadow, border deepens | 320 ms |
| Card image | 1.04 scale inside a clipped frame | 600 ms |
| Primary button | 1 px lift, burgundy-tinted shadow, 0.995 press | 120–200 ms |
| Nav item | mocha-050 pill appears under the pointer | 120 ms |
| Mega menu / search panel | 6 px rise + 0.995 scale from top | 200 ms |
| Toast | 10 px rise | 240 ms |
| Mobile buy bar | rises from the bottom edge | 320 ms |
| Cart badge | 1.22 pop when the count increases | 360 ms |
| Gallery | 280 ms crossfade on thumbnail change | 280 ms |
| Below-fold sections | 14 px rise + fade, once, on intersection | 560 ms |

Guardrails: reveals are applied only after JS marks the document (`js-motion`), so a failed
script or a no-JS visit never hides content; `prefers-reduced-motion: reduce` collapses every
duration to 0.01 ms and forces revealed sections visible; focus rings are never animated; hover
lifts are behind `@media (hover: hover)` so touch devices do not get stuck states; print forces
all revealed content visible.

Cost: +3.7 kB CSS and +2.0 kB JS uncompressed, no new requests, no third-party animation
library. The render-blocking path is unchanged.

## 5. Navigation and information architecture

**Top level (6 items, under Hick's 7–8 ceiling):** Shop all · By concern · By ingredient · Sets ·
Our standards · Help.

- **By concern** and **By ingredient** open mega-menus grouped by symptom, each row showing a live
  product count. The menu is a `<button aria-expanded>` + panel, closable with Escape and by
  clicking outside; it is not a hover-only menu.
- **Sets** and **Our standards** are single destinations, not menus — they answer "what do I buy
  first" and "why should I trust this".
- **Help** is a first-class top-level item: support is not buried in the footer.
- Faceted filtering lives in the left rail on shop pages (concern, skin type, format, ingredient),
  each facet showing counts. There are no nested header chains beyond one level.
- Mobile: a native `<dialog>` menu with 48 px rows, focus trapped by the platform, and a visible
  close control. The header keeps logo, search, account and cart at all times.

URL contract: `/shop/?concern=dry` is shareable and restores the filtered state; facets update the
URL with `replaceState` so the back button is not polluted.

## 6. Intent search

The search field is a symptom resolver, not a product-name matcher.

**Index.** Every product is indexed on name, subtitle, format, concerns and concern synonyms.
Nine concerns carry 4–7 synonyms each (`dry` ← dry, tight, flaky, dehydration, stinging after
washing…), 48 synonyms in total.

**Ranking** (`assets/js/app.js`):

| Signal | Weight |
| --- | --- |
| Exact name match | 100 |
| Name prefix | +30 |
| Product belongs to the matched concern | +70 |
| Token match in name | 18 per token |
| Token match in body text | 6 per token |

**Interface.** Typing opens a combobox after a 120 ms debounce: a concern row ("Dryness and
tightness — 5 products matched") first, then matching products with thumbnail, name, price and
format. Concern matching needs 3+ characters; product matching starts at the first character.
Counts are computed from the live catalog, not hard-coded. Arrow keys move the active option,
Enter navigates, Escape closes and returns focus to the field.

**Zero results** offers the three nearest concerns and a "Browse all 8 products" link; it never
shows a dead end. The search response also writes an `aria-live` status ("5 products matched").

**Instrumentation:** `search` with `query`, `matched_count`, `intent`, `result_clicked`. The KPI
is search-to-ATC lift versus non-search sessions, not raw query volume.

## 7. Performance: the 3-second rule

### 7.1 Budgets and measured values

| Metric | Budget | Home | PDP |
| --- | --- | --- | --- |
| HTML (gzip) | ≤ 30 kB | 6.9 kB | 7.9 kB |
| CSS + JS + fonts + catalog (gzip) | ≤ 60 kB | 34.9 kB | 39.8 kB |
| Total first viewport | ≤ 90 kB | **43.6 kB** | **49.5 kB** |
| Requests before load | ≤ 12 | **9** | **8** |
| Web font requests | 0 | 0 | 0 |
| Third-party scripts | 0 | 0 | 0 |
| LCP image | ≤ 60 kB | 3.2 kB (hero 960w) | 1.8 kB (packshot 480w) |

Measured locally over HTTP/1.1 with encoded-body sizes; a CDN with Brotli will be smaller. Full
per-route table in `docs/build-report.md`; all 50 WebP files total 271 kB.

### 7.2 Image pipeline

- Source art is vector, rendered to WebP at 480w and 960w (plus 960/1600 for the hero), quality 82,
  effort 6. Deterministic, no manual export step.
- `width`/`height` on every `<img>`; `srcset`/`sizes` tuned per slot; `loading="lazy"` on
  everything below the fold; `fetchpriority="high"` on the LCP image only.
- Hero preload matches the `srcset`/`imagesize` exactly — a mismatch would double-download the
  image, so the two are generated from the same values.
- No CSS background images for content; no icon fonts (inline SVG, 20 px grid).

### 7.3 Script and font policy

Zero analytics, zero tag manager, zero chat widget, zero A/B testing SDK in this build.
That is the only reliable way to hit a 3-second budget on mid-range mobile. When measurement is
added, it goes through one first-party endpoint with:

- `defer` + ≤ 6 kB gzip;
- no synchronous third parties before first paint;
- server-side events for purchase (never a pixel-only purchase);
- a quarterly script inventory with owner and removal date.

### 7.4 Portable output (runs without a server)

The build rewrites every internal URL relative to the page (`./`, `../`, `../../`) and stamps the
depth on `<html data-base>`; links created at runtime read that value. The same `dist/` therefore
works on a static host (clean directory URLs) and from disk (`file://`), with no server process
and no localhost. Canonical, Open Graph, JSON-LD and sitemap URLs stay absolute by design.

Verified in Chrome from `file://`: hard reload, header and card navigation, symptom search, add to
cart,
cart totals, checkout validation, facets, and the returns dialog all work with zero console
errors. Trade-off: addresses on disk include `index.html`, which a host hides.

### 7.5 What is not proven here

No field Core Web Vitals data exists for this build (no RUM, no production origin). Local numbers
show the payload is small enough that 3G-fast LCP is plausible, not guaranteed. Before launch,
measure LCP/INP/CLS on a throttled Moto G4 profile and on the real CDN; treat the budgets above as
the gate.

Caching plan for production: immutable `assets/img/*` (1 year), hashed CSS/JS (1 year), HTML
`s-maxage=60, stale-while-revalidate=600`, Brotli at the edge.

## 8. Checkout without surprises

### 8.1 Shape

Three steps, one decision per screen: **Contact → Delivery → Payment**. Guest is the default and
only path; "Already have an account? Sign in" is a secondary link inside step 1, never a gate.
The progress bar shows all three steps with the current one marked in text as well as colour.

**Currency and tax.** Amounts are authored in whole rupees — not converted at runtime — and
formatted with Indian digit grouping (₹12,999; ₹1,20,000). GST is estimated at 18% from the
delivery PIN code and shown before payment; displayed prices exclude GST. Checkout collects an
Indian state/UT and a 6-digit PIN, with numeric keypads for PIN, card, expiry and CVC.

### 8.2 Field contract

| Field | Type | Inputmode | Autocomplete | Validation |
| --- | --- | --- | --- | --- |
| Email | email | email | `email` | Format; inline error on blur and before advancing |
| First / last name | text | — | `given-name` / `family-name` | Non-empty |
| Address | text | — | `address-line1` | Non-empty |
| City | text | — | `address-level2` | Non-empty |
| State / UT | select | — | `address-level1` | Required (Indian states and UTs) |
| PIN | text | **numeric** | `postal-code` | `[1-9][0-9]{5}` (6 digits) |
| Card number | text | **numeric** | `cc-number` | Luhn + length, formatted in groups of 4 |
| Expiry | text | **numeric** | `cc-exp` | MM/YY, not in the past |
| CVC | text | **numeric** | `cc-csc` | 3–4 digits |
| Card name | text | — | `cc-name` | Non-empty |

Validation runs on blur (only after a value exists or the field is already marked invalid) and on
step advance. Errors are inline, tied with `aria-describedby`, announced via `aria-invalid`, and
summarised at the top of the step with links to each field. The summary receives focus, so a
keyboard or screen-reader user lands on the list of problems, not at the top of the page.

Verified behaviour: empty submit → summary visible, 1 field flagged (email), focus moved to the
summary; `not-an-email` → "Enter an email address in the format name@example.com."; correcting
the value clears `aria-invalid` without a resubmit.

### 8.3 No-surprises disclosure matrix

| Cost or term | PDP | Cart | Checkout |
| --- | --- | --- | --- |
| Item price | yes, with per-ml | yes | yes |
| Shipping cost + free threshold | yes | yes | yes, selectable |
| Tax | "calculated at checkout before payment" | estimated | estimated, labelled |
| Return window and who pays | yes | yes | yes, under the pay button |
| Delivery estimate | "ships today if ordered by 2 pm IST" | date range | date range |

Policy values are single-sourced (`src/catalog.mjs` → `policies`) and rendered into every surface,
so the PDP cannot disagree with checkout.

### 8.4 Trust at the point of conversion

Directly beneath the pay/add-to-cart button: encrypted-checkout line, 30-day returns with prepaid
label, PCI-DSS Level 1 processor statement, and card-brand marks only if actually supported. The
trust row is text-first; a badge image is not a substitute for a sentence.

### 8.5 Anti-dark-pattern rules

- No pre-checked upsells, no countdown timers, no "only 2 left" unless inventory is real.
- No account creation after payment to "see your order" — the confirmation page and email both
  carry the tracking link.
- No hidden fees introduced at payment; the total shown in step 2 is the total charged.
- Cancelling or going back never loses entered data.

### 8.6 Production integration requirements

The reference checkout validates and simulates. Before launch it must call a PCI-compliant
processor (Stripe Payment Element, Adyen Components or equivalent) with:

- tokenisation in the processor's iframe/fields, card data never touching our DOM or logs;
- 3-D Secure handled in-place with a visible pending state;
- idempotency keys on order creation;
- server-side GST calculation (or a tax service) replacing the flat 18% demo estimate;
- order confirmation email with tracking link, sent before the page unloads its state.

## 9. Trust and privacy architecture

**Claims register.** Every trust statement on the site must map to one of: a measured test, a
certification with a certificate ID, a policy with a linked page, or a live count from the order
database. Current statements and their basis:

| Statement | Basis | Where |
| --- | --- | --- |
| "6,400 verified orders" | live order count, excludes cancelled | home proof strip |
| "12% squalane by weight" | formulation record | PDP, card, JSON-LD |
| "30-day returns, opened or not" | published policy | PDP, cart, checkout, help |
| "Encrypted checkout, PCI-DSS Level 1 processor" | processor attestation | under CTA |
| "Fragrance-free" | formulation sheet | PDP ingredients |

**Badges.** No seal is displayed unless it is current and linkable to the issuer. Trust marks are
placed where anxiety peaks (under the CTA, next to the card fields), not in a footer badge farm.

**Privacy.** The site sets no cookies and loads no third-party requests. Cart state
lives in `localStorage` only. For production: consent-gated analytics, data minimisation on order
records (no card data, no marketing consent bundled with purchase), a published retention period,
and a one-click data export/delete path in the account panel. "Privacy and data" is a visible
account section, not a policy link.

| Page | Tab | Skip link → header → nav → main → footer |
| Mega menu | Enter/Space, Esc | Opens; Esc closes and returns focus to trigger |
| Search | ↓/↑, Enter, Esc | Moves options, navigates, closes and refocuses input |
| Size selector | ←/→ | Native radio group changes selection and price |
| Quantity | Tab, Enter/Space | Stepper buttons are real buttons |
| Dialogs (menu, filters, returns) | Esc | Native `<dialog>` closes, focus restored |
| Checkout | Tab, Enter | Inline validation; error summary receives focus |

Measured on the current build: first Tab reaches the skip link; "dry skin" returns 6 suggestions
with the concern row first; Esc closes the panel and leaves focus in the field; arrow key on the
size group moves ₹6,999 → ₹9,799.

### 10.3 Screen reader notes

- Cart changes announce "Barrier Repair Balm added to cart. 2 items now in cart."
- Search announces the match count after each keystroke, debounced.
- The shipping progress meter has an accessible name and value, not just a coloured bar.
- Decorative illustrations carry empty `alt`; product images describe the object and its size.

### 10.4 Motion

All transitions are ≤ 160 ms and disabled under `prefers-reduced-motion: reduce`. No parallax,
no auto-advancing carousels, no hover-only information.

### 10.5 Test evidence

- axe-core (`wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa`): **0 violations** across 9 routes ×
  2 viewports (`docs/a11y-report.md`).
- Static audit: labels, headings, landmarks, JSON-LD, inputmodes, policy copy (`docs/build-report.md`).
- Manual: keyboard path, focus visibility, dialog focus return, error summary focus, 320 px reflow.

### 10.6 Limits of this evidence

axe-core catches roughly a third of WCAG failures. Not yet tested: real screen-reader passes
(VoiceOver/NVDA), 400% zoom on iOS Safari, switch access, and cognitive-load testing with users.
Those are required before a public accessibility statement is published.

## 11. Structured data and agentic commerce

### 11.1 Graph per template

| Template | JSON-LD types |
| --- | --- |
| Global | `Organization`, `WebSite` + `SearchAction` |
| Home | `Organization`, `WebSite` |
| Shop | `ItemList` (8 products) + `BreadcrumbList` |
| PDP | `Product` (with `Offer` per size, `AggregateRating`, `Review`), `BreadcrumbList` |
| Help | `FAQPage` |
| Cart / checkout / account | `BreadcrumbList` only — transactional pages are not indexed |

### 11.2 Offer completeness

Each size is its own `Offer` with a stable `@id` (`#offer-CK-BB-050`), `price`, `priceCurrency`,
`priceValidUntil`, `availability`, `itemCondition`, `seller`, `eligibleQuantity`,
`shippingDetails` (rate, destination, handling and transit time) and
`hasMerchantReturnPolicy` (30 days, prepaid label, return shipping paid by merchant). `Product`
also carries `sku`, `mpn`, `category`, `additionalProperty` (size, format, fragrance-free) and
three image URLs including the in-scale shot.

### 11.3 Parity rules (enforced in CI)

- The JSON-LD price must equal the rendered price, per size. The audit fails otherwise.
- `availability` must match the stock line rendered on the page.
- `priceValidUntil` must be in the future; regenerate on price change.
- Product `@id` and `url` are canonical and never change with campaigns.
- No review markup without a real review. This build emits no `review` or `aggregateRating`
  node at all; add both only once the first verified review exists.

### 11.4 Discovery surfaces to feed next

Structured data is the floor, not the ceiling. To be usable by agents and shopping feeds:

1. **Merchant feed** (Google Merchant Center, Meta, Bing) with GTIN where available, condition,
   shipping weight and tax category. This build has no GTINs — assign or request them.
2. **Product availability endpoint** (`/api/stock.json`) for agentic checkers, cached 60 s.
3. **Policy URLs** in JSON-LD pointing at human-readable pages, not fragments.
4. **Stable identifiers** across feed, JSON-LD and order system (SKU is the join key).

## 12. Retention: the 80/20 post-purchase path

| Surface | Job | Rule |
| --- | --- | --- |
| Order confirmation | Prove the order exists | Order number, total, delivery window, tracking link, one-click account creation (optional) |
| Account → Orders and tracking | Answer "where is it" without support | Timeline with timestamps, carrier + tracking, one primary action |
| Account → Buy it again | Shorten the second order | Previous items with current price and stock, one-click add |
| Account → Returns | Remove the fear of buying | 30-day window stated, reason select, prepaid label, status timeline |
| Account → Addresses / Payment | Reduce checkout friction | Stored with processor; only brand + last four shown |
| Guest tracking | Same value without an account | Order number + email form; no login wall |

Lifecycle triggers that should be wired in production: day 3 (delivery check), day 21 (usage
check + review request), day 45 (replenishment window based on 50 ml usage), day 60 (win-back with
the same SKU, not a discount blanket). Every email links to a page that works signed out.

Instrumentation: `track_order_view`, `reorder_click`, `return_start`, `return_complete`,
`account_created_after_purchase`. The retention KPI is 60-day repeat rate by acquisition cohort,
not email open rate.

## 13. Support architecture

- **One click from anywhere:** Help is a top-level nav item and a footer column.
- **Six categories, keyword titles:** Orders and tracking · Returns and refunds · Shipping and
  delivery · Products and routines · Account and payment · Our standards. 24 answers total.
- **Titles are the search queries** customers actually type ("Where is my order", "Cancel before
  dispatch"), not internal taxonomy.
- **Minimal sidebar:** four links, no nested tree, no chat popup covering the cart. The help page
  keeps the global header and cart count visible.
- **Self-service first:** every answer ends in an action (track, start return, change address) or a
  contact route with expected response time.
- **Deflection metric:** help sessions ending in a completed action / total help sessions;
  secondary: contacts per 100 orders.

### 14.2 Experiment backlog

| # | Hypothesis | Primary metric | Decision rule |
| --- | --- | --- | --- |
| 1 | Showing the in-scale image as gallery slide 2 (not 3) raises ATC on mobile | PDP → ATC | Ship if +5% relative at 95% confidence; stop at 2 weeks or 8k sessions |
| 2 | Defaulting the shipping method to the cheapest option with the delivery date visible reduces step-2 abandonment | Checkout completion | Ship if abandonment −3 pts; watch AOV for downgrade cannibalisation |
| 3 | Putting "30-day returns, prepaid label" directly under the CTA raises ATC | PDP → ATC | Ship if +3% relative; segment new vs returning |

Sample-size discipline: at 3% baseline conversion, detecting +5% relative needs ~120k sessions per
arm. Until volume supports that, ship changes backed by usability testing and measure guardrails
(refund rate, support contacts) rather than claiming significance.

### 14.3 Dashboards

One funnel per device class: PDP view → ATC → checkout start → step 3 → purchase. One retention
view: 30/60/90-day repeat by first SKU. One quality view: LCP p75, INP p75, CLS p75, JS error rate,
help contacts per 100 orders.

## 17. Decisions and deviations

| Decision | Why | Cost |
| --- | --- | --- |
| Body copy uses Mocha Ink, not Mocha Cream | 1.41:1 is unreadable; 4.79:1 passes | One tonal step added inside the same hue |
| Header band is Mocha Cream | Keeps the 30% present on editorial pages; anchors the F-pattern | Slightly warmer first impression |
| Mobile PDP uses a sticky buy bar | Puts price + CTA in the thumb zone at first paint | Duplicate add-to-cart control for AT users; both are labelled |
| Home first viewport is 84% Latte | Reading surface, no panels | Declared deviation from literal 30% |
| PDP mobile accent at 11.2% | Sticky CTA + selected state | 1.2 pts above the 10% ceiling, capped at 12% |
| System fonts | 0 kB, no CLS, no FOIT | Serif differs by OS |
| Generated product art | Deterministic, tiny payload, exact scale reference | Not a substitute for photography |
| Static build, no framework | Auditability, 41 kB pages | Rebuild step required for content changes |
| Relative URLs + `data-base` | Runs from disk and from a host with one build | `index.html` visible in file:// addresses |
| INR pricing, GST, PIN, Indian states | Matches the requested market and currency | Tax is still a flat 18% demo estimate |
